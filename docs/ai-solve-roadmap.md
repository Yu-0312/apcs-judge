# AI 解題功能更新：設計說明與提高正確率的架構

本文件記錄這次對 `ai-solve.html` 及相關頁面的更新，重點放在「如何用系統設計把 AI 解題的正確率往上推」。所有改動維持原本的安全底線：純前端、自備金鑰、任何 AI 程式碼都要經使用者明確同意才執行、「公開範例相符 ≠ AC」的誠實標示不退化。

---

## 一、這次做了什麼（四個方向）

### ② 每步驟選型 + 深度思考模型
- `data/service-config.js` 的 `gemini` 區塊新增 `steps`（讀題／解題／教練／深度解題各自的預設模型）、`deepThink`（thinking 預算、輸出上限、對拍輪數、逾時）與 `solveMaxOutputTokens`。
- 讀題改用最省的 `gemini-3.1-flash-lite`（每次必跑，降這層最省成本）；解題預設 `gemini-3.5-flash`；勾「深度思考」時解題換 `gemini-3.5-pro` 並帶 thinking 預算。
- `callGemini(parts, schema, opts)` 改為 step-aware：依步驟選模型、可覆寫 `maxOutputTokens`／`thinkingBudget`／`timeoutMs`。解題輸出上限從 8192 提高到 16384（深度思考 32768），避免長詳解＋程式碼被截斷。
- 讀題／教練的自動退回不會覆寫使用者為「解題」選定的模型。

### ① 強化驗證：隨機測資對拍（differential testing）
- 公開範例只有 1～2 筆，過關不代表正確。深度思考模式在公開範例過關後，再請 AI 產生兩支「純標準庫」Python：一支**隨機測資產生器**（吃種子、輸出小規模合法測資）、一支**一定正確但可以慢的暴力解**。
- `stressTest()` 逐一：種子 → 產生器 → 暴力解（標準答案）→ 候選解，比對輸出。第一個不一致就是**反例**，把它（含輸入、暴力解輸出、候選輸出）回灌給解題 prompt 重寫，形成「找反例 → 修正」的迴圈。
- Python 候選解全在瀏覽器 Pyodide 本地跑（預設 60 輪、不吃額度）；C/C++/Java 候選需送 Judge0，故降到 8 輪以免觸發公用額度限制。產生器與暴力解一律本地 Python。
- 結果頁與錯題本都標示「通過 N 組對拍（仍不代表 AC）」，維持誠實。

### ③ 教練模式看使用者的程式碼
- 確認頁新增「教練批改我的程式」子模式：貼上自己的程式碼，教練用蘇格拉底式提問指出「哪一類輸入會出錯／哪一行邏輯有問題」，**不給修好的程式**，沿用既有的完整程式碼攔截（`coachResponseHasCode`）。
- 維持教練模式的鐵律：**不執行任何程式、不送 Judge0**（CI 契約 `check-data.js` 會擋住教練區塊呼叫任何執行函式）。
- `COACH_SCHEMA` 增加 `on_track`，讓模型自評學生上一輪想法是否走對方向，作為自適應提示的依據。

### ④ 站內整合
- 題庫 `index.html` 每題工具列新增「🤖 用 AI 解」，帶 `?problem=<id>&lang=<lang>` 開新分頁。
- `ai-solve.html` 支援該深連結：直接從 `judge-problems.js` 帶入確認頁、跳過讀題（省一次 API），沿用 index 的安全 id 驗證（只接受已知題目、擋 `../` 等）。
- 解題結果新增 `related_topics`（核心觀念關鍵字）連回教學頁複習。
- 錯題本 `mistakes.html` 新增「🔁 今天該複習」篩選；AI 錯題寫入 `nextReviewAt`（預設 +2 天）與 `masteryState`，接上既有的間隔複習 UI（原本只有判讀題有）。

## 二、提高正確率的整體架構（重點）

把「解一題」拆成一條**逐層過濾 + 反饋修正**的管線，每一層都在做兩件事之一：**讓模型更容易一次答對**，或**更早、更便宜地抓出錯誤並回饋修正**。

```
讀題(結構化+限制條件)
   → 解題(限制→複雜度推導 + 陷阱檢查 + 思考預算)
      → 公開範例一致性檢查(3 次，抓 WA 與不穩定輸出)
         → 隨機對拍(對暴力解找反例)            ← 深度思考
            → 反例回饋修正(重寫，最多 N 版)
               → 通過才解鎖詳解 + 存錯題本
```

### 槓桿 1：讓輸入更「可解」——結構化 + 限制條件
讀題階段除了忠實轉錄題意，另外**單獨抽出限制條件**（N 範圍、數值上下界、時間限制、特殊保證）成獨立欄位，使用者可在確認頁校正。這是正確率的隱藏關鍵：模型知道「N 到 10^6」就不會端出 O(N²)。

### 槓桿 2：讓模型先想再寫——複雜度推導 + 陷阱清單
解題 prompt 要求模型**先從限制推估所需複雜度**、說明所選演算法為何夠快，再逐一檢查 APCS 常見陷阱（輸入格式與換行、0/1 索引、整數溢位、邊界 N=0/1、讀到 EOF 的多筆測資）。因為結構化輸出的欄位順序是 `approach → complexity → code`，模型會先產出思路與複雜度，等於強制一段「先計畫再寫碼」的思考鏈。

### 槓桿 3：更強的模型 + 思考預算（深度思考）
高級數題目換旗艦推理模型並給 thinking 預算。這是對「難題一次答對率」最直接的提升，代價是延遲與成本，所以設計成單一開關的 opt-in，預設仍用快而省的 flash。

### 槓桿 4：驗證從「範例」升級到「對拍」（最大的一步）
公開範例太少，是原本「相符 ≠ AC」最大的來源。對拍用一支獨立的暴力解當**近似 oracle**，在數十組隨機小測資上與候選解比對，能抓出範例抓不到的邏輯錯與邊界錯。這把信心從「1～2 筆範例相符」實質推進到「N 組獨立隨機輸入與暴力解一致」。它仍不是 AC 證明（不含官方隱藏測資、也受限於暴力解本身正確與測資分佈），但假陽性大幅下降。

### 槓桿 5：反饋式修正迴圈
公開範例不符或對拍找到反例時，把**具體反例（輸入／預期／實得）**回灌 prompt 讓模型重寫，而非只說「錯了」。反例愈具體，修正命中率愈高。深度思考再多給一次修正額度。

### 槓桿 6：誠實的解鎖閘門
只有公開範例三次相符且一致、（深度思考時）對拍也無反例，才解鎖完整詳解並標記 `sampleChecked`/`stressChecked`；`verified` 永遠是 `false`。避免把「看起來對」誤傳成「保證對」。

## 三、尚未實作、但已設計好的下一步（依效益排序）

1. **Best-of-K 自我一致性**：同一題以較高 temperature 生成 K 份候選，各自過範例＋對拍，取通過者；多份都過但對拍輸入上分歧時以多數決並標示。`service-config.js` 的 `deepThink.candidates` 已保留此旋鈕。**未做的原因**：每份候選都要走「執行前明確同意」的安全閘，K 份會讓同意流程變得繁瑣，需要先設計「一次同意涵蓋整批」的 UX。效益高，建議下一個做。
2. **TLE（複雜度）探針**：另外產生一組「最大規模」測資，只跑候選解並量測本地耗時，超過門檻就標「可能 TLE」。補上「範例都小、看不出會不會超時」的盲點。
3. **多圖上傳**：APCS 題目常跨頁，目前只吃單張圖（`imageB64`）。
4. **含圖表題目保留原圖給解題**：目前解題只用確認過的文字（防注入的刻意設計），會遺失格線／樹狀圖等資訊；可對「圖表關鍵」題目選擇性保留原圖。
5. **以站內 300 題參考解答做少樣本（few-shot）風格範例**：提升輸出格式與風格一致性。
6. **模型集成**：flash 與 pro 各解一份互相對照，分歧時再深挖。

- **cacheVersion**：這次改了 `service-config.js` 內容，但為避免跨頁大量改動，暫未更動 `cacheVersion`（仍為 `20260717f`）。正式部署前建議 bump（例如 `20260718a`）並同步所有頁面的 `service-config.js?v=` 與 `chat-widget.js?v=`，CI 的 `check-data.js` 會驗證一致性。
- **模型可用性**：`service-config.js` 內的型號（`gemini-3.5-flash` / `gemini-3.1-flash-lite` / `gemini-3.1-pro` / `gemini-3.5-pro`）以 2026-07 可用型號為準；若 Google 調整，改這一個檔即可，前端會對不在清單內的 step 模型自動退回安全預設。CI 已擋退役與已公告停用（如 2.5 系列）的型號。
- **Judge0 額度**：C/C++/Java 的對拍受公用 Judge0 CE 限制，已降到 8 輪；若要更充分的對拍，建議接自架或帶金鑰的 Judge0。
- **測試**：本次改動已通過 repo 內所有 `check-*.js` 契約檢查，並以 JSDOM 煙霧測試確認 `ai-solve.html` 載入無 runtime 錯誤、深連結可帶入題目；對拍迴圈以單元測試確認能抓出反例。仍建議在真實瀏覽器＋實際 Gemini 金鑰做一次端到端驗證（含深度思考、教練批改、`?problem=` 深連結）再上線。
