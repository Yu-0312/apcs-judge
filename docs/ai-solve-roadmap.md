# AI 解題功能更新：設計說明與提高正確率的架構

本文件記錄這次對 `ai-solve.html` 及相關頁面的更新，重點放在「如何用系統設計把 AI 解題的正確率往上推」。所有改動維持原本的安全底線：純前端、自備金鑰、任何 AI 程式碼都要經使用者明確同意才執行、「公開範例相符 ≠ AC」的誠實標示不退化。

---

## 一、這次做了什麼（四個方向）

### ② 每步驟選型 + 深度思考模型
- `data/service-config.js` 的 `gemini` 區塊新增 `steps`（讀題／解題／教練／深度解題各自的預設模型）、`deepThink`（thinking 預算、輸出上限、對拍輪數、逾時）與 `solveMaxOutputTokens`。
- 讀題改用最省的 `gemini-3.1-flash-lite`（每次必跑，降這層最省成本）；解題預設 `gemini-3.5-flash`；勾「深度思考」時解題換 `gemini-3.5-pro` 並帶 thinking 預算。
- `callGemini(parts, schema, opts)` 改為 step-aware：依步驟選模型、可覆寫 `maxOutputTokens`／`thinkingBudget`／`timeoutMs`。解題輸出上限從 8192 提高到 16384（深度思考 32768），避免長詳解＋程式碼被截斷。
- 讀題／教練的自動退回不會覆寫使用者為「解題」選定的模型。

### ① 強化驗證：隨機測資對拍（differential testing）
- 公開範例只有 1～2 筆，過關不代表正確。深度思考模式在公開範例過關後，再請 AI 產生兩支「純標準庫」Python：一支**隨機測資產生器**（吃種子、輸出小規模合法測資）、一支**一定正確但可以慢的暴力解**。
- `stressTest()` 逐一：種子 → 產生器 → 暴力解（標準答案）→ 候選解，比對輸出。第一個不一致就是**反例**，把它（含輸入、暴力解輸出、候選輸出）回灌給解題 prompt 重寫，形成「找反例 → 修正」的迴圈。
- Python 候選解全在瀏覽器 Pyodide 本地跑（預設 60 輪、不吃額度）；C/C++/Java 候選需送 Judge0，故降到 8 輪以免觸發公用額度限制。產生器與暴力解一律本地 Python。
- 結果頁與錯題本都標示「通過 N 組對拍（仍不代表 AC）」，維持誠實。

### ③ 教練模式看使用者的程式碼
- 確認頁新增「教練批改我的程式」子模式：貼上自己的程式碼，教練用蘇格拉底式提問指出「哪一類輸入會出錯／哪一行邏輯有問題」，**不給修好的程式**，沿用既有的完整程式碼攔截（`coachResponseHasCode`）。
- 維持教練模式的鐵律：**不執行任何程式、不送 Judge0**（CI 契約 `check-data.js` 會擋住教練區塊呼叫任何執行函式）。
- `COACH_SCHEMA` 增加 `on_track`，讓模型自評學生上一輪想法是否走對方向，作為自適應提示的依據。

### ④ 站內整合
- 題庫 `index.html` 每題工具列新增「🤖 用 AI 解」，帶 `?problem=<id>&lang=<lang>` 開新分頁。
- `ai-solve.html` 支援該深連結：直接從 `judge-problems.js` 帶入確認頁、跳過讀題（省一次 API），沿用 index 的安全 id 驗證（只接受已知題目、擋 `../` 等）。
- 解題結果新增 `related_topics`（核心觀念關鍵字）連回教學頁複習。
- 錯題本 `mistakes.html` 新增「🔁 今天該複習」篩選；AI 錯題寫入 `nextReviewAt`（預設 +2 天）與 `masteryState`，接上既有的間隔複習 UI（原本只有判讀題有）。

## 二、提高正確率的整體架構（重點）

把「解一題」拆成一條**逐層過濾 + 反饋修正**的管線，每一層都在做兩件事之一：**讓模型更容易一次答對**，或**更早、更便宜地抓出錯誤並回饋修正**。

```
讀題(結構化+限制條件)
   → 解題(限制→複雜度推導 + 陷阱檢查 + 思考預算)
      → 公開範例一致性檢查(3 次，抓 WA 與不穩定輸出)
         → 隨機對拍(對暴力解找反例)            ← 深度思考
            → 反例回饋修正(重寫，最多 N 版)
               → 通過才解鎖詳解 + 存錯題本
```

### 槓桿 1：讓輸入更「可解」——結構化 + 限制條件
讀題階段除了忠實轉錄題意，另外**單獨抽出限制條件**（N 範圍、數值上下界、時間限制、特殊保證）成獨立欄位，使用者可在確認頁校正。這是正確率的隱藏關鍵：模型知道「N 到 10^6」就不會端出 O(N²)。

### 槓桿 2：讓模型先想再寫——複雜度推導 + 陷阱清單
解題 prompt 要求模型**先從限制推估所需複雜度**、說明所選演算法為何夠快，再逐一檢查 APCS 常見陷阱（輸入格式與換行、0/1 索引、整數溢位、邊界 N=0/1、讀到 EOF 的多筆測資）。因為結構化輸出的欄位順序是 `approach → complexity → code`，模型會先產出思路與複雜度，等於強制一段「先計畫再寫碼」的思考鏈。

### 槓桿 3：更強的模型 + 思考預算（深度思考）
高級數題目換旗艦推理模型並給 thinking 預算。這是對「難題一次答對率」最直接的提升，代價是延遲與成本，所以設計成單一開關的 opt-in，預設仍用快而省的 flash。

### 槓桿 4：驗證從「範例」升級到「對拍」（最大的一步）
公開範例太少，是原本「相符 ≠ AC」最大的來源。對拍用一支獨立的暴力解當**近似 oracle**，在數十組隨機小測資上與候選解比對，能抓出範例抓不到的邏輯錯與邊界錯。這把信心從「1～2 筆範例相符」實質推進到「N 組獨立隨機輸入與暴力解一致」。它仍不是 AC 證明（不含官方隱藏測資、也受限於暴力解本身正確與測資分佈），但假陽性大幅下降。

### 槓桿 5：反饋式修正迴圈
公開範例不符或對拍找到反例時，把**具體反例（輸入／預期／實得）**回灌 prompt 讓模型重寫，而非只說「錯了」。反例愈具體，修正命中率愈高。深度思考再多給一次修正額度。

### 槓桿 6：誠實的解鎖閘門
只有公開範例三次相符且一致、（深度思考時）對拍也無反例，才解鎖完整詳解並標記 `sampleChecked`/`stressChecked`；`verified` 永遠是 `false`。避免把「看起來對」誤傳成「保證對」。

## 三、第二次更新（2026-08）：自我審查、信心自評、刁鑽測資、best-of-2、TLE 探針

在槓桿 2（先想再寫）與槓桿 4（對拍）之上，再加五個限制／自我檢查機制，全部只動 `SOLVE_SCHEMA`／`GENTEST_SCHEMA` 與對應 prompt、`stressTest()`、`doSolve()`、結果頁，安全底線不變（新增的候選 B 一樣走同一個「執行前明確同意」畫面，且會把程式碼實際列出來，不是隱性擴權）。

- **自我審查（self_check）**：`SOLVE_SCHEMA` 在 `code` 之後、`explanation` 之前插入 `self_check` 欄位，要求模型逐條回報「輸入格式／索引起點／整數溢位／邊界情形／多筆測資」是否已處理。因為結構化輸出照欄位順序生成，等於強制模型在寫詳解前先回頭核對一次自己的程式，發現問題要直接改 `code` 而不是回報未修的已知問題。結果頁會顯示這段自我審查。
- **信心自評（confidence）**：新增 `confidence`（low/medium/high）與 `confidence_reason`。信心低時結果頁會用醒目提示建議開「深度思考」重解一次；目前只做提示、不強制擋詳解，避免和既有的「範例＋對拍」解鎖閘門邏輯衝突或造成無窮重試。
- **輸出格式逐字核對**：`solvePrompt` 新增第 3 點思考步驟，要求模型在心中用每組公開範例逐字元模擬輸出（含空白、換行、大小寫），比事後只靠 `normOut()` 容錯更早攔下格式類 WA。
- **AI 手工設計的刁鑽測資（tricky_cases）**：`stressPrompt` 現在會把候選解的 `approach` 與 `code` 一併交給模型，請它「針對這份實作」手工設計 0～3 組最可能出錯的測資（不是亂數），`stressTest()` 會先跑這些，再跑原本的隨機對拍。手工測資通常比小規模亂數更容易命中真正的邏輯漏洞，且不需要額外的 API 呼叫（與 generator/brute 同一次請求拿到）。
- **TLE 探針**：`GENTEST_SCHEMA` 新增 `max_scale_input`（規模拉到限制上限的測資，不需要暴力解算出正確輸出）。對拍與刁鑽測資全數通過後，`stressTest()` 額外用這組測資跑一次候選解並量測執行時間——C/C++/Java 取 Judge0 回報的 `time`（排除排隊與網路來回，門檻 `TLE_WARN_MS = 3000`），Python 在 Pyodide 本地量牆鐘時間並放寬到 `TLE_WARN_MS_PY = 8000`（瀏覽器比原生慢一個量級），補上「範例與對拍都刻意用小規模、看不出複雜度是否選錯」的盲點，結果頁會標「可能 TLE」。
- **Best-of-2 自我一致性（簡化版）**：深度思考模式下，第一次產生解答時，額外用 `solvePrompt(..., {independent:true})`（要求「不要參考任何先前解法，從頭獨立推導」）+ 較高 temperature（0.9）獨立生成候選 B，**於同一個執行前確認畫面**列出程式碼，同一次核可涵蓋兩者。對拍階段會重播候選 A 已知（輸入,暴力解答案）配對到候選 B 身上比對，不需要為 B 另外生成/執行對拍程式。全部一致時顯示「可信度較高」；有分歧時只顯示為參考資訊，**不會**用來擋掉或替換候選 A（避免多一層「兩個都可能是錯的」判斷邏輯讓誠實閘門變複雜）。`service-config.js` 的 `deepThink.candidates`（目前 3）作為開關：設為 1 可關閉此功能而不動程式碼。

以上都已通過 repo 既有的 `check-data.js` / `check-index-contract.js` / `check-client-state.js` 契約檢查（新增欄位皆為既有 schema 之外的擴充，未觸碰任何被檢查的固定字串）。

## 四、第三次更新（2026-08）：讀題正確性

前面兩次更新都在強化「解題」，讀題階段本來只靠使用者在確認表單裡人工核對。這次補上四個機制，兩個是不用呼叫 AI 的本地決定性檢查、兩個是 AI 層面的補強：

- **本地逐字核對測資（`checkTestcasesAgainstSource`）**：純文字模式下，把 AI 轉錄的每組範例 input/expected_output（空白正規化後）拿去比對是否為原始 `problemText` 的子字串；找不到就在該組測資旁標警告。零 API 成本、決定性判斷，抓「AI 順手修正或推測了範例內容」這類最危險的錯誤。圖片模式沒有原文可比對，會跳過。
- **限制條件數字核對（`checkConstraintNumbers`）**：只抓原文中「與比較符號（≤ ≦ < ＜ ≥ ≧ > ＞）或秒／ms／MB／KB／byte **直接相鄰**」的數字，檢查是否都出現在 AI 產生的 `constraints` 欄位裡；漏抄的數字會列出來提醒使用者核對。刻意不取整行、也不把 `=` 與 `~` 納入觸發符號：敘述句（「第 2 天記錄 = 31 度」）與程式碼片段（「`i < n`」）常與限制同行，整行取數字會大量誤報。比對用逐數字整體比對而非子字串，否則 `256` 會讓漏抄的 `25` 被誤判為已抄。
- **讀題 best-of-2（`compareReads`）**：讀題模型是最省的 flash-lite，多讀一次成本很低。第二次獨立讀題（temperature 0.6）完成後，只比對「會直接影響解題正確性」的欄位——限制條件、範例測資、建議語言；三者中兩次讀題結果不一致，代表題目在那裡有歧義或難以辨識（圖片模糊、敘述含糊），會攤開兩個版本讓使用者自己核對，而不是默默相信其中一個。
- **AI 自報不確定點（`uncertain_notes`）**：`READ_SCHEMA` 新增 `uncertain_notes`，讓模型讀題時老實列出「哪裡看不清楚／原文本身含糊」，確認表單最上方會列出來，把使用者的注意力導到真正該覆核的地方，而不是要求每個字都重新看一遍。

四項都顯示在確認表單的 `#read-checks` 區塊與對應的測資列，且都只是「提示」不會擋流程——使用者仍可直接修改或忽略後繼續，維持既有的人工確認為主、AI 檢查為輔的設計。

### 第三次更新的已知取捨
- best-of-2 讀題讓每次「讀題」動作變成 2 次 Gemini 呼叫（兩次並行發出，因此幾乎不增加等待時間，但成本加倍）；因為讀題模型本來就是全站最便宜的一層，這個取捨還算合理，但若要做「使用者可關閉」的開關，目前還沒做。
- 限制條件數字核對是正規表示式啟發式，遇到題目本身用「小於」「不超過」等純中文描述限制（沒有符號、沒有秒/MB 等單位字）就抓不到，屬於已知盲點，不是漏洞而是保守設計（寧可漏報也不要因為太敏感洗版）。

## 五、第四次更新（2026-08）：對拍 oracle 驗證

對拍的正確性完全建立在「AI 產生的暴力解一定正確」這個假設上；但暴力解本身也是 AI 寫的，可能有 bug。`stressTest()` 現在會先拿**公開範例**去驗證暴力解——執行錯誤或任何一組對不上，就直接判定這支暴力解不可信任，整段對拍略過（`reason` 會說明原因），而不是拿一支可能有錯的 oracle 去誤判候選解、白白浪費修正額度，或反過來讓一份其實有錯的候選解因為「剛好跟錯的暴力解一致」而被誤判通過。這個驗證只用公開範例（已知正確），不需要額外呼叫 AI。

## 六、尚未實作、但已設計好的下一步（依效益排序）

1. **Best-of-K（K≥3）＋多數決**：目前只做到 best-of-2、且分歧時不影響判定；若要更進一步可依 `deepThink.candidates`（預設 3）真的生成 K 份，多數決與少數派標示需要更完整的合意 UX 設計。
2. **多圖上傳**：APCS 題目常跨頁，目前只吃單張圖（`imageB64`）。
3. **含圖表題目保留原圖給解題**：目前解題只用確認過的文字（防注入的刻意設計），會遺失格線／樹狀圖等資訊；可對「圖表關鍵」題目選擇性保留原圖。
4. **以站內 300 題參考解答做少樣本（few-shot）風格範例**：提升輸出格式與風格一致性。
5. **信心自評與對拍結果掛勾**：目前 `confidence` 只在結果頁提示，未來可考慮「低信心 + 非深度思考」時自動追加一輪刁鑽測資或對拍，而不必使用者手動重開深度思考。
6. **讀題 best-of-2 可關閉的開關**：目前固定多讀一次，可以加到確認頁或 service-config，讓在意成本的部署者關掉。

## 七、部署前須知

- **cacheVersion**：這次改了 `service-config.js` 內容，但為避免跨頁大量改動，暫未更動 `cacheVersion`（仍為 `20260717f`）。正式部署前建議 bump（例如 `20260718a`）並同步所有頁面的 `service-config.js?v=` 與 `chat-widget.js?v=`，CI 的 `check-data.js` 會驗證一致性。
- **模型可用性**：`service-config.js` 內的型號（`gemini-3.5-flash` / `gemini-3.1-flash-lite` / `gemini-3.1-pro` / `gemini-3.5-pro`）以 2026-07 可用型號為準；若 Google 調整，改這一個檔即可，前端會對不在清單內的 step 模型自動退回安全預設。CI 已擋退役與已公告停用（如 2.5 系列）的型號。
- **Judge0 額度**：C/C++/Java 的對拍受公用 Judge0 CE 限制，已降到 8 輪；若要更充分的對拍，建議接自架或帶金鑰的 Judge0。
- **測試**：本次改動已通過 repo 內所有 `check-*.js` 契約檢查，並以 JSDOM 煙霧測試確認 `ai-solve.html` 載入無 runtime 錯誤、深連結可帶入題目；對拍迴圈以單元測試確認能抓出反例。仍建議在真實瀏覽器＋實際 Gemini 金鑰做一次端到端驗證（含深度思考、教練批改、`?problem=` 深連結）再上線。
